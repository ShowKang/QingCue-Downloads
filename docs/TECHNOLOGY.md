# 技术难点与解决思路

本文以**方向性叙述**说明 QingCue（轻词）在工程上要解决的几类问题，以及采取的整体思路。
不给出可直接复现的实现细节：不涉及计算公式、实现取值与内部类型命名。

## 1. 核心矛盾：识别是不确定的，阅读体验必须是确定的

流式语音识别输出的文本假设有三个特征：

- **不完整**：一句话在说完之前只能得到片段。
- **会修正**：后续音频可能导致前文被改写或吞并。
- **有抖动**：相邻两次输出之间可能出现增删。

如果直接把识别文本映射到稿件位置，界面就会随修正来回跳动。QingCue 的处理方向是**把不确定性关进对齐层**：

- 对外的进度是一根**单调递增的轴**，只允许前进或停留，不允许后退。
- 中间结果用于**平滑**，稳定结果用于**定位**；两者职责分开。
- 当新的识别结果与已确认位置冲突时，以「已确认」为准，冲突信息只用于后续修正的参考，不直接驱动画面。

这样，识别器的所有反复都被消化在内部，渲染层拿到的始终是一个稳定位置。

## 2. 从稀疏事件到连续运动

语音识别是**事件式**的：说完一个词才可能输出一次结果。而人眼期待的是**连续**的高亮移动。二者之间存在天然的颗粒度差。

解决方向是**在事件之间做有约束的插值**：

- 用最近的朗读进度估计当前节奏，画面按该节奏平滑移动。
- 长时间没有新证据时，画面会逐渐停止，而不是凭时间无限前进。
- 新的稳定结果到达时，以它为准做校正，并让校正以视觉可接受的方式完成，而不是瞬移。

这带来一个必然取舍：**快读时的跟手性**与**慢读/停顿时的稳定性**无法同时最优。系统选择偏稳定，代价是语速突变后的短时滞后。

## 3. 容错对齐：朗读不会严格照着稿子

真实朗读包含重复、回读、跳读、口误、改口、插入语气词。如果按「逐字精确匹配」来设计，任何一处偏差都会让进度卡死。

QingCue 的思路是**以稿件为锚、以识别为证据**的容错对齐：

- 匹配以**句子**为天然边界。句子是演讲者自然的停顿单位，也是容忍局部偏差的最小单元。
- 对重复与回读，识别为「已读过的内容」，保持当前位置而不是回退。
- 对跳读，会被识别为进度前进；跨度过大时可能短暂停留再追上。
- 对口误，不要求逐字命中，允许局部不一致；连续、大范围的不一致时，系统倾向停在原位等待更多证据。

方向上的原则是：**宁可慢一拍，不可乱跳**。错误的推进比滞后的推进对演讲者伤害更大。

## 4. 延迟预算：每一层都不能排队

从「开口」到「画面动」是一条串行链路：采集 → 识别 → 对齐 → 渲染。任何一层积压都会累积成可感知的延迟，而且这种延迟一旦产生就很难靠下游追回。

工程上的应对是**按层拆解延迟，并让各层并发**：

- 采集与识别之间保持稳定的流水，不随运行时长增长。
- 识别持续输出中间结果，不必等一句话结束；对齐层消费的是「流」，而不是「句」。
- 跨句切换的准备工作在当前句内完成，减少切换等待。
- 渲染层只做增量更新，避免整块重绘造成的布局抖动与掉帧。

这条链路的难点不在于单层快，而在于**长稳**：连续朗读数十分钟时，不能有隐性的内存增长或队列增长。

## 5. 视觉稳定：界面是跟随系统的「显示器」

渲染层承担两个容易互相冲突的目标：

- **准确**：高亮位置要反映真实朗读进度。
- **稳定**：画面不能抖、不能闪、不能突然跳行。

做法是把界面当作**一条单一时间轴**的投影：所有视觉元素（高亮、滚动、引导线）都由同一个位置驱动，避免多个状态源各自为政。同时把更新粒度控制在「只改变必要部分」，减少浏览器重排与重绘。

滚动本身也做取舍：完全跟随会让快读时画面剧烈移动，完全固定又会让高亮跑出可读区。系统选择**有界的视口跟随**——高亮接近可读区边缘时才滚动，并让滚动与高亮位移同源，避免两者互相追赶。

## 6. 离线推理的资源约束

本地运行意味着算力、内存、磁盘都由用户机器承担，不能假设有服务器级的资源。方向性做法：

- 识别在本地完成，模型与运行时的选择优先考虑**CPU 可用性**而非峰值精度。
- 模型可选、可按需获取并校验完整性；不使用语音跟随时不加载模型。
- 音频、文本、稿件全部留在本机；不存在「上传—返回」的网络往返，既降低延迟也消除隐私风险。

## 7. 桌面壳层与 Web 界面的边界

界面用本地 Web 视图表达排版与动效，窗口、输入、生命周期、数据持久化由原生壳负责。这条边界的价值是**把系统集成的复杂度挡在业务之外**：

- 壳层保证单实例、置顶、快捷键与安装升级等平台行为。
- 视图层只处理呈现与交互，不感知设备与文件系统。
- 两侧通信保持**低频、批量、幂等**，避免高频消息引发的抖动。
